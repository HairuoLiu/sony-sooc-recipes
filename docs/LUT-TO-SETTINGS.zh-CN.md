# 从 .cube 到相机设置：一次转换的全过程

<p align="center"><a href="LUT-TO-SETTINGS.md">English</a> · <b>简体中文</b></p>

> 本文回答两个问题：**「你是怎么把 LUT 目录里的 .cube 变成相机里的一个配方的？」** 和
> **「为什么最后只剩下 ±1 / ±2 这么几个数字？」**
>
> 一句话结论：**这不是转码，是测量之后重写。** 一个 33³ 的 LUT 有 35,937 个节点，被压成大约
> 10 个标量；而这 10 个标量里，**没有一个**能表达「只改某个色相」或「只改某一段影调」。

---

## 1. 两步管道

### 步骤 1 — 测量：把 35,937 个节点压成 ~10 个数

脚本：`build/analyze_luts.py`（相机模拟批次 18 条）、`measure_leica_luts.py`（徕卡三条）。
做法：读 `.cube` → 采样若干代表色 → 归纳成「性格指标」。**只读取事实，不动文件。**

| 指标 | 怎么测 | 落到哪个相机参数 |
|---|---|---|
| `mid_contrast` | 中性灰 0.3→0.8 的输出亮度斜率（1.0 = 不变） | `con` |
| `sat_ratio` | 9–10 个色块的 Lab 色度比 `co/ci`，取均值 | `sat` |
| `cast_a` | 灰阶序列的 a\* 均值（红 +/绿 −） | `gm` |
| `cast_b` | 灰阶序列的 b\* 均值（黄 +/蓝 −） | `ab` |
| `shadow_lift` | 5% 灰的输出亮度 − 输入亮度 | `dro` |
| `highlight_compress` | 95% 灰的输入 − 输出 | **无处可去** |
| 逐色块色相偏移 | Lab 色相角差（度） | **无处可去** |
| 逐色块饱和比 | 单块色度比 | **被均值吃掉** |

### 步骤 2 — 逆模型：把指标折成整数

`measure_leica_luts.py` 里的 `derive_settings()`，全部逻辑就是这些：

```python
sat = clamp(round((sat_ratio - 1.0) * 20), -3, 3)
con = clamp(round((mid_contrast - 1.0) * 20), -3, 3)
ab  = clamp(round(cast_b / 3.0), -3, 3)
gm  = clamp(round(cast_a / 3.0), -3, 3)
dro = clamp(round(shadow_lift * 40), 0, 6)
style = "NEUTRAL" if (sat_ratio < 0.85 and mid_contrast < 1.0) \
        else ("VIVID" if sat_ratio > 1.1 else "STD")
```

三个除法常数（20 / 3 / 40）、一次四舍五入、一次夹紧——**这就是全部**。它的三个直接后果：

- 反差差异在 **±2.5%** 以内 → `con = 0`，信息直接消失。
- `sat_ratio` 高于 1.15 或低于 0.85 → **撞上 ±3 的天花板**，多出来的力度被截断。
- 灰阶没有偏色（a\*≈0、b\*≈0）→ `ab = gm = 0`，**哪怕彩色区域偏色很重**。因为公式只看中性灰。

> **两个批次的差别。** 相机模拟（18 款）与胶片（38 款）走的是**同一条测量**，但没有套公式：
> 数值是照着测量结果手写的（`build/add_camera_sims.py`、`build/add_film_batch.py`）。原因是公式在
> 表达力不够的地方会给出明显错误的结论，手写可以引用厂商公开描述、也可以把取舍写进 `note`。
> 徕卡那三条（CNT / CLS / ETN）是唯一跑过公式的，因为当时的要求是「精确对照」。

## 2. 相机侧一共只有哪些选项

槽位 ID 与可写范围来自 fork 的 `MainActivity.java`（**每个参数就是一个字节槽**），
可达范围来自索尼菜单与上游反向工程。

| 槽位 | 参数 | 应用内可写 | **机身菜单可达** |
|---|---|---|---|
| `0x01070175` | 创意风格 `style` | 1–13 | 13 选 1 |
| `0x01070187` | 饱和 `sat` | −16…+16 | **±3（7 档）** |
| `0x01070178` | 反差 `con` | −8…+8 | **±3（7 档）** |
| `0x0107018a` | 锐度 `sharp` | −8…+8 | ±3 |
| `0x0107031c` | PP3 色彩矩阵开关 | 0 / 1 | 菜单里根本不显示 |
| `0x01070018` | 色温 `kelvin` | 25–99（即 2500–9900K） | ✅ 直接可调 |
| `0x01070017` / `0x01070016` | 白平衡微调 `ab` / `gm` | −7…+7 | ±7（15 档） |
| `0x010706f1` | 图片效果 `pe` | 0–13 | 14 选 1 |
| `0x010700b8` | 曝光补偿 `ev` | −15…+15（1/3 EV 步进） | ✅ 直接可调 |
| `0x01070104` | DRO | 0–6 | 7 档 |

合计：**1 个风格枚举 + 大约 8 个全局整数。** 全部是全局的——没有任何一项能按色相、按影调、
或按画面区域分别取值。

> **应用能写得比菜单更狠，但没意义。** `sat = −9` 这类值 APK 能写进去、相机也存得住，但机身
> 创意风格滑块封顶 ±3——你一旦手碰到菜单，多出来的力度就被吸附掉了。`docs/MAPPING-RECIPES.md` §2.4
> 列了现在这 11 条超范围的配方。

## 3. 逐项损失——这才是「有出入」的根本原因

| 真实的 LUT 能做到 | 相机能做到 | 后果 |
|---|---|---|
| 每个色相单独调饱和 | **一个**全局 `sat` | 逐色相信息被**取均值**吃掉 |
| 旋转单个色相（比如让蓝天偏青而肤色不动） | 完全不能旋转色相 | 色相信息**整体丢弃**，连字段都没有 |
| 任意色调曲线（S 曲线、黑位抬升、高光滚降） | **一个** `con` 标量（a6000 无 Picture Profile） | 曲线形状无字段可放 |
| 阴影偏青 + 高光偏暖（分色调） | **一个**全局 `ab`/`gm` | 分色调降级成整体偏色 |
| 逐节点 35,937 × 3 个输出值 | ~8 个标量 | 见下 |

**这是量级差距，不是精度差距。** 所以结论只能是近似，而且出入通常不是「力度差一点」，
而是「某一个色相或某一段影调的方向做反了」。

## 4. 完整工作示例：`LEICA CLS.cube`

**测量**（33³；数据来自 `leica_lut_diff.txt`）：

```
中调反差 mid_contrast = 1.177        饱和比 mean = 0.791
灰阶色偏 a* = -1.11  b* = +1.17      阴影提升 shadow_lift = -0.026

逐色块饱和比： R 0.93 · G 0.70 · B 0.80 · C 0.71 · M 0.95 · Y 0.75
               skin 0.77 · foliage 1.03 · sky 0.49
逐色块色相偏移： skin +21° · sky -11° · C -7° · Y +5°
```

**折成设置**：

```
sat = round((0.791 - 1) * 20) = round(-4.18) = -4  → clamp → -3   ← 撞天花板
con = round((1.177 - 1) * 20) = round(+3.54) = +4  → clamp → +3   ← 撞天花板
ab  = round( 1.17 / 3) = round( 0.39) = 0
gm  = round(-1.11 / 3) = round(-0.37) = 0
dro = round(-0.026 * 40)           = -1  → clamp → 0
style = STD
```

最终表达：**`STD, sat -3, con +3, ab 0, gm 0, dro 0`**。四个必须看清的损失：

1. **两支参数都撞了天花板。** LUT 实际需要 sat≈−4、con≈+4，7 档网格给不出来。
2. **sky 被砍到 0.49，而 foliage 反而升到 1.03——方向相反。** 一个全局 `sat = −3` 会把 foliage
   也一起减饱和，这就是方向性错误，不是力度不够。
3. **skin +21° 的色相旋转完全没有落地**，因为没有对应字段。
4. **`shadow_lift` 是负的**（LUT 在压暗阴影），而 `dro` 只能提亮，公式夹到 0 → **这一整轴等于丢弃**。

## 5. 为什么目录里那三条莱卡是另一套数字

`leica-contemporary` / `leica-classic` / `leica-eternal` 三条的 `source` 是 **`recipe-lab`**（上游项目），
不是 `authored-here`。上面那套推导是我为了核对做的**对照实验**，结论是三条全都对不上——所以当时
只汇报差异、**没有覆盖**。差异不只是力度，有的方向相反：

| | LUT 实测性格 | 推导设置 | 上游目录配方 |
|---|---|---|---|
| Contemporary | 收饱和、S 曲线（中调 +9.6%）、灰阶无色偏 | STD · sat −2 · con +2 · dro 0 | STD · sat +1 · con +1 · dro 6 |
| Classic | 明显收饱和、S 曲线（+17.7%）、微暖 | STD · sat −3 · con +3 · dro 0 | STD · sat −1 · con +2 · ab +1 · dro 6 |
| Eternal | **高反差**（+31%）、品红–蓝冷偏 | STD · sat +2 · con +3 · ab −1 · gm +1 | **NEUTRAL 低反差** · sat −3 · ab +1 · dro 3 |

Eternal 那一行最典型：LUT 是高反差、冷偏，上游配方是低反差、暖调——**几乎全反**。

## 6. 自己核对

```bash
python build/analyze_luts.py      # 相机模拟批次 18 条的实测指标（打印到终端）
python measure_leica_luts.py      # 徕卡三条：实测 vs 推导 vs 上游 → 写 leica_lut_diff.txt
```

两个脚本都**只读 .cube、只输出结果**，不会改动注册表。要新增条目，走
[`docs/ADDING-FILTERS.md`](ADDING-FILTERS.zh-CN.md)。

## 7. 结论

- 这不是「LUT 转码」，是**读懂 LUT 的性格，再用相机有限的几个旋钮重新调一遍**。
- 表达力差距是量级性的：LUT 是三维查找表（逐色相、逐影调），相机是约 8 个全局标量。
- 因此**一定会有出入**，而且出入往往表现为「某个色相 / 某段影调方向做反了」，而不是「强度差一点」。
- 想真正还原 LUT，唯一的技术路径是 `film-studio-matrix` 那套硬件 3×3 矩阵 + 1024 点 Gamma，
  但它绑死 a5100 固件 1.10、需要一个不随仓库分发的基础 APK、许可为非商用。
  详见 [`docs/ARCHITECTURE.zh-CN.md`](ARCHITECTURE.zh-CN.md) §3。
